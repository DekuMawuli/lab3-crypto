Overview: The project is a TCP client for Applied Cryptography Lab 3, speaking the protocol in `crypto_message_spec_v2.md`. It does two independent things against the course cloud server: (1) fetches an AES-256 key, encrypts a file locally, sends the encrypted file and key to the server, and gets the decrypted file back; (2) fetches a key, computes the course's custom HMAC over a file locally, and sends the file, key and HMAC to the server to be checked. The HMAC is the nested-hash construction from Lecture 7 (`ψMD(ko || ψMD(ki || x))` with `ki = k ⊕ 0x36...`, `ko = k ⊕ 0x5c...`), not RFC 2104 HMAC, so it must be hand-implemented rather than taken from a library.

Project Requirements
1. The code will be written in Python 3.
2. The user interface will use tkinter, matching the client sketch in `Lab 3.pdf` (Server IP, Port, Username, Message type, Get Key, file-to-encrypt + save-as with Browse buttons, Encrypt, progress bar, status line). Message types must cover `get_key`, `decrypt`, and `verify_hmac`.
3. The UI will let the user choose a file and will derive the names of its companion files (`.enc`, `.key`, `.hmac`, `.hmackey`) automatically from that base file's name, per section 5/6 of the spec, rather than asking the user to pick each one separately.
4. Network I/O will not run on the UI thread; the UI must stay responsive during a request.
5. Server IP, port, and username are read from a local, gitignored config file (not hardcoded, not committed), since the spec says to keep the username out of shared repositories.
6. Message framing follows spec section 3 exactly: 4-byte big-endian header length, UTF-8 JSON header (max 1000 bytes), optional binary payload. All reads loop until the requested number of bytes has arrived — a single `recv()` call is not assumed to return everything.
7. AES encryption uses AES-256-GCM with the exact layout in spec section 5: 12-byte random nonce (fresh per file) || ciphertext || 16-byte tag, no associated data. The key for `decrypt` is never generated by the client — only keys returned by `get_key` are used.
8. The HMAC is computed exactly as in spec section 6 / Lecture 7's nested-MAC construction: SHA-256, `Ki = K XOR 0x36*32`, `Ko = K XOR 0x5c*32`, `HMAC = SHA256(Ko || SHA256(Ki || x))`, operating on raw bytes at every step (never hex text). The standard `cryptography` library's HMAC module is not used for this.
9. A `verify_result` of `FAILED` is a normal, valid outcome and must be displayed differently in the UI from an `error` reply — it is not treated as a program error.
10. Before any networking, the framing and AES-GCM implementations are checked against the test vectors in spec section 9, and the HMAC implementation is checked against both the "hello world" vector and the empty-file vector in the same section.
11. A local fake server, implementing section 3 framing and canned replies on `127.0.0.1`, is used to exercise the client's error-handling paths (bad username, oversized payload, malformed header) without depending on the real network.
12. Files over the spec's payload limit (1,048,576 bytes; 1,048,548 bytes of plaintext for encryption) are rejected by the client before sending, not left for the server to reject.
13. The key, at no point, is written to a log or printed to the console; it only ever appears in the `.key` / `.hmackey` companion file and on the wire.

Open questions
- Whether to support re-running `decrypt`/`verify_hmac` on a previously generated `.enc`/`.hmac` set without re-fetching a key, or whether every run starts from a fresh `get_key`.
- Whether the UI needs to support files beyond the one selected per run (spec section 1 only requires "a file of your choice" for the HMAC half).
